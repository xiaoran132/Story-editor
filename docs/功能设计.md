# 1 功能设计

> ## 阅读边界：愿景与当前实现
> 本文是 **PRD / 产品愿景**，其中大量“支持”“提供”的描述是目标能力，**不代表已经实现**。当前可运行范围、接口、数据字段、测试和接手顺序，请先看 [开发交接手册.md](开发交接手册.md)；工程约束看 [`../CLAUDE.md`](../CLAUDE.md)。
>
> 截至 **2026 年 7 月 28 日**：游玩闭环（生成、审校、回溯、读档）已完成；创作前端、社区、支付、成就、流式输出尚未实现。产品优先级是先验证游玩留存，再扩张创作与社区。

本平台定位为：
**“AI驱动的互动剧情共创社区”**，用户既是玩家也是创作者，通过 AI Agent 协作完成剧情生成、体验、分享与再创作，形成“创作—体验—传播—变现”的闭环生态。

整体功能分为四大模块：

- 🎮 玩家体验模块
- ✍️ 创作者编辑模块
- 🌐 社区与共创模块
- 💰 商业化与激励模块

------

## 1.1 玩家模块（剧情体验端）

玩家以“游玩剧情”为核心，体验由 AI + 作者共创生成的互动故事。

### 1.1.1 剧情游玩界面

主要由三大区域组成：

1）**剧情显示区**

- 展示当前故事文本、角色对话
- 支持文字 + 图片 + 语音（后期扩展）
- AI根据玩家选择动态生成后续剧情

2）**自由选择区（高自由度输入）**
不同于传统固定选项，支持两种方式：

- 系统推荐选项（AI生成）
- 玩家自由输入行为描述（自然语言）

例如：

> “逃跑” / “说服对方” / “直接攻击” / 玩家自定义输入：“假装投降然后偷钥匙”

3）**状态与属性面板（固定显示，对于非游戏性的剧本也可以不显示）**

- 角色属性：生命值、智力、魅力、金钱、好感度等
- 背包与关键道具
- 当前世界观与角色背景摘要
- 实时随剧情变化更新

------

### 1.1.2 时间线与节点系统（树状剧情）

- 每一次选择形成一个节点
- 所有剧情形成**树状时间线结构**
- 支持：
  - 回溯任意节点
  - 重玩不同分支
  - 对比不同选择的结果

类似《底特律：变人》的时间线系统，并可标注：

- 选择概率（多少玩家走过此路线）
- 热门结局路径
- 作者推荐路线

------

### 1.1.3 存档与历史记录

- 自动保存关键节点
- 手动存档 / 云端存档
- 历史事件列表（可回看剧情片段）
- 可将某条完整时间线导出为：
  - 小说文本
  - 剧本格式
  - 分享链接
  - 互动小说游戏（对于小型小说生成，类似橙光，或者其他类型，ai生成代码）
  - 微短剧

------

## 1.2 社区模块（内容发现与互动）

### 1.2.1 剧情社区主页

提供内容浏览与推荐功能：

- 分类浏览（悬疑 / 恋爱 / 科幻 / 校园 / 剧本杀等）
- 关键词搜索
- 推荐榜单：
  - 热度榜
  - 好评榜
  - 新作榜
  - 作者榜

------

### 1.2.2 剧情详情页（模型主页）

每个剧情作品拥有独立主页，包含：

- 剧情简介
- 作者信息
- 标签分类
- 点赞 / 收藏 / 评论
- 打赏与关注作者
- 游玩入口

扩展功能：

- **节点分享**：玩家可分享自己经历的某条剧情分支给他人直接体验，直接将已发现的节点载入到玩家自己的类似仓库吧。
- **付费模式**（作者自己决定）：
  - 免费
  - 买断制
  - 类似小说一章一章一样，可以对剧情的纵向深度计费，以一个选项节点类比成一个章节，考虑到深度越大，分支节点越多，也可以根据深度增加价钱。

------

### 1.2.3 个人主页

展示用户信息与行为数据：

- 用户信息（头像、昵称、粉丝、关注）
- 已收藏作品
- 游玩记录
- 个人作品
- 成就系统（创作数量、游玩时长、社区贡献）

------

## 1.3 创作者模块（编辑与共创）

创作者可通过可视化工具制作剧情模型。

### 1.3.1 剧情编辑器（核心）

功能包括：

- 导入本地素材，音乐，图片等

    - 初始剧情模板
    - 剧情节点编辑（可视化树状结构）
- 支持 AI 协助生成
  - 剧情草稿
  - 对话润色
  - 分支建议
  - 初始剧情模板
- 模型切换，支持对图片、剧情、人物等单独配置
------

### 1.3.2 作品发布与管理

- 发布到社区
  - 设置简介
  - 设置付费方式
    - 买断制
    - 深度付费
    - token计费
  - 设置访问权限
- 导出
  - 小说
  - 短剧
  - 互动式
    - 游戏
    - 短剧

  - 点赞、收藏、游玩人数

  - 盈利

# 3 MVP 范围与优先级

第 1 章罗列的是**完整产品愿景**，并非一次性交付范围。按 “创作—体验—社区” 最小闭环拆分优先级，避免失焦。

| 优先级 | 目标 | 功能范围 |
|--------|------|----------|
| **P0（MVP 三件套）** | 打通「创作一个作品 → 玩一局 → 社区看到」最小闭环 | 账号（注册/登录/JWT/个人资料）；创作者编辑器基础版（世界观、角色、初始剧情、`initial_state` 属性定义、AI 配置）；剧情游玩（**游玩会话** + 节点树生成 + 属性面板 + 回溯）；基础社区（作品列表/详情/点赞/评论） |
| **P1** | 让体验完整、内容可被发现 | 存档/读档（会话续玩）；**AI 服务真实对接**（`/generate`、`/continue`，含流式）；搜索与榜单（热度/好评/新作/作者）；收藏、关注作者；节点/路线分享 |
| **P2** | 增强表现力与商业化 | 多模态素材（封面/背景/立绘/BGM）；付费解锁 / 打赏 / 收益分成；成就与积分；WebSocket 实时流式推送 |
| **P3** | 生态与 IP | 接力共创（多人协作、分支共建、主题挑战）；一键导出小说/剧本/短剧/漫画/互动游戏；专家点评；三方分享与海报；热门 IP 世界观合作 |

> **P0 验收口径**：一个创作者能创建作品并定义任意属性键（如 `hp/gold/好感度`）；一个玩家能进入该作品、输入自由文本或选推荐项、看到 AI 生成的下一节点、属性面板随 `state_delta` 更新、能回溯到任意历史节点重新分叉；作品发布后在社区列表可见、可点赞评论。**AI 未接入前用桩数据（固定/模板文本）验证节点树与属性链路。**

# 4 用户角色与权限

平台角色基于 `users.role` 字段（现有实现），权限自低到高：

| 角色 | 说明 | 关键权限 |
|------|------|----------|
| **游客** | 未登录 | 浏览社区、查看已发布作品详情（只读） |
| **玩家（user）** | 注册用户，默认角色 | 游玩、存档、点赞/收藏/评论、分享、关注作者 |
| **创作者** | 玩家发布过作品即具备（非独立账号体系） | 创建/编辑/发布作品、上传素材、配置 AI、查看自己作品的数据统计 |
| **运营** | 内部 | 维护标签字典（`story_tags`）、配置榜单、内容推荐 |
| **管理员** | 内部 | 内容审核、下架作品、封禁用户（`users.status`） |

> **待澄清**：玩家 ↔ 创作者共用同一账号，任何玩家都可创作。

# 5 开放问题与待决策

以下是设计评审中发现的、需要在编码推进前拍板的冲突与模糊点（按影响排序）：

### 5.1 架构与实现一致性（高）
1. ~~**`play_sessions` 缺失**~~ ✅ **已实现**：`model.PlaySession` + `repository/play_session.go` 已建，`main.go` 的 `AutoMigrate` 已纳入 `&model.PlaySession{}`；`service.PlayService`（`StartSession` / `MakeChoice` / `Backtrack` / `GetSession`）与 `/api/v1/play/*` 路由已打通，游玩链路可端到端跑通（最小页面 `templates/index.html` 已验证：开局→选择→AI 生成→属性更新→回溯）。
2. **JSONB 的处理方式**：Go model 目前把 `world_config`/`state_delta`/`current_state` 定义为 `string`，与「后端直接做 JSONB `||` 合并」的设计前提不符。需决定：改用 `datatypes.JSON` + 原生合并，还是在应用层反序列化后合并再写回。
3. **架构定位**：`设计思路.md` 的 5 个 “service” 是**逻辑模块/未来拆分方向**，当前实现为 Go 单体扁平分层。本文档按「MVP 单体、后期按需拆分微服务；AI 服务独立进程」定位。

### 5.2 属性系统语义（高）
4. ~~**增量对非数值属性失效**~~ ✅ **已解决（AI + 合并层）**：属性分为 `number`（数值累加）/ `scalar`（覆盖式）/ `set`（集合增删）三类，创作者在 `world_config.attributes` 声明每键类型。Python `story_graph.normalize` 按类型规整 LLM 输出的 `state_delta`，Go `service.mergeState` 按类型合并（未声明类型的键回落为「数值累加否则覆盖」，兼容老作品），两端语义由 `play_merge_test.go` 锁定。
   > 遗留（低）：`assist/world` 生成的 `attributes` 目前无「与 `initial_state` 键一致」的硬校验；创作侧发布接口尚未做 `world_config` schema 校验。
5. **三份状态的一致性成本**：见 `设计思路.md`「关键数据流与前后端契约」，需明确以 `current_state` 为准、`state_snapshot` 仅作回溯缓存的约定并强制事务化。

### 5.3 AI 不确定性（中）
6. **「对比不同选择 / 重玩分支」vs AI 随机性**：`temperature` 较高时同一选择不可复现。已生成节点应**持久化复用**（回到旧节点看到的是原内容），仅在玩家主动「新开分支」时才请求 AI 生成——需在交互设计中区分「查看已有分支」与「探索新分支」。

### 5.4 社区与商业化语义（中）
7. **玩家/创作者账号是否统一**：见第 4 章，建议统一（降低创作门槛），需确认。
8. **节点分享的语义**：节点归属私有 `session`，「分享给他人直接体验」是**复制到对方会话**还是**共享只读路线**？两者数据结构不同（复制需新建 session + 节点，共享需路线快照表）。当前 `is_public` + `visit_count` 暗示共享统计，但分享入库路径未定义。
9. **「按深度计费」在分叉树上的定义**：`price_config.per_depth` 把「深度=章节」，但同一 `depth` 有多个分叉节点。需重新定义计费单位（如按「解锁的路径长度」而非绝对 depth）。
10. **接力共创 vs 单一 player 归属**：节点树目前绑定单个 `session/player`，多人协作缺权限与分支合并模型，属 P3，暂记录不展开。

### 5.5 后端工程化（本轮评审新增）

11. **服务层 context 传递断层（中）**：`repository` 层方法已接收 `ctx context.Context`（设计正确），但 `service` 层普遍用 `context.Background()` 自造 context，`handler` 也未把 `c.Request.Context()` 往下传——整条链路是断的。后果最明显处：`play.MakeChoice` 调用 AI 服务（可能数十秒）用的是 `Background()`，**客户端中断/请求超时时该慢调用不会被取消**，也没有统一 deadline / trace 贯穿。建议：`service` 方法签名统一加 `ctx`，`handler` 传 `c.Request.Context()`，一路打通到已就绪的 `repository`。改动机械、面中等、风险低。
12. **工程化待办（低）**：
    - 无优雅关闭——`r.Run()` 阻塞，缺信号处理与 `http.Server.Shutdown` 连接排空；
    - `seed` 每次启动都跑，应移到 flag/env 开关之后，避免生产环境误注入；
    - `community` handler 仍为全桩（已知 TODO）。

### 5.6 未来可能会出现的问题
13. **中后期上下文剧增** 在文本达到一部短篇小说量级时，上下文暴涨所带来的
  - token 需求过高
  - 幻觉
  - rag 检索困难
  - 思考时间长

> 标注 **（高）** 的三项中，第 1、4 项已实现/解决；**仅剩第 2 项（JSONB 处理方式）** 建议在继续写业务代码前拍板，否则属性合并链路后续可能返工。
