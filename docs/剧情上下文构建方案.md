# 剧情上下文构建方案（续写时"已发生剧情"如何喂给 LLM）

## 问题

续写（`MakeChoice` → agent `/continue`）时，需要把"已发生剧情"作为上下文给到 LLM。
**最初实现是全量重放**：`FindPath` 取根→当前路径上的**每个节点**，把每段 `content` + `choice_text`
逐字拼进提示（`story_graph.py` 的 `prepare`）。

缺陷：
1. 上下文随剧情深度 **O(depth) 线性膨胀**，深剧情迟早撑爆上下文窗口、触发超长报错。
2. 同一批历史正文每一步被重复发送、重复计费。
3. 无上限保护、无降级。

## 四种策略对比（本质只有"窗口 / 摘要 / 检索"三类；节点树是承载它们的存储载体）

| 维度 | ①滑动窗口+快照 | ②滚动摘要(每步重算) | ③RAG 检索 | ④节点树增量摘要 |
|---|---|---|---|---|
| 上下文随深度 | O(N) 常数上限 | O(1) | O(k) 常数上限 | O(1) |
| 额外 LLM 调用 | 无 | 每步 +1 次 | 无(需向量化) | 0（折进 generate） |
| 延迟 | 低 | 高 | 中 | 低 |
| 落库改动 | 无 | 存 summary | 向量库+embedding | 加 summary 列（迁移） |
| 回溯正确性 | 天然对 | 需重算/缓存 | 天然对 | 天然对 |
| 叙事细节保真 | 近段全保、远段全丢 | 有损、会漂移 | 按需精准召回 | 有损、会漂移 |
| 工程量 | 最小 | 中 | 最大 | 中 |

## 决策

- **当前（demo）阶段：采用 ① 滑动窗口 + 状态快照兜底。** 零 schema 改动、零 Go 改动，当场消除"撑爆窗口"风险。
- ③④ 作为演进方向记录于本文，暂不实现。

### ① 落地现状（已实现）

- 位置：`agent/app/graph/story_graph.py` 的 `_write_history_window`（`prepare` 调用）。
- 参数：`agent/app/config.py` 的 `Settings.history_window`（默认 **8**，可用环境变量 `HISTORY_WINDOW` 覆盖；`<=0` 表示不限制、退回全量重放）。
- 逻辑：历史 ≤ window 时全量渲染；超出时**保留「开局第 1 段 + 最近 (window-1) 段」原文**，中间以
  `（……中间 N 段剧情从略，其结果已反映在下方"当前属性"中……）` 折叠。
- **为什么快照能兜底**：属性以带类型的增量合并，`current_state` 始终是**截至当前的完整状态快照**
  （唯一事实来源）。早期剧情的*结果*已沉淀其中，故折叠早期正文不破坏状态一致性，仅损失远段**叙事细节**。
- 已知局限：折叠掉的远段细节（伏笔、NPC 名）在深层续写中不可见——由后续 ③/④ 弥补。

## 未来方案

### ④ 节点树增量摘要（推荐的下一步）

**核心思想**：借 append-only 节点树，把"前情提要"一次生成、永久复用。

- **数据**：`story_nodes` 增列 `summary`（截至该节点的累计前情提要）。
- **生成（零额外 LLM 调用）**：让 `/continue` 的 `STORY_SYSTEM` 在返回 `content` 的同时**多吐一个
  `summary`** = 父节点 `summary` 滚动更新后的版本；`AIResult`/schema 增字段，新节点落库时一并写入。
- **续写上下文** = `父节点.summary` + 最近 1~2 段原文 + 当前选择 → **O(1)**，与深度无关。
- **回溯零成本正确**：回溯到节点 X 再分叉时直接用 `X.summary`（它已涵盖截至 X 的一切），
  无需回退/重算——这是节点树 append-only 结构独有的红利（②做不到，故②贵）。
- **要处理的点**：
  - schema 迁移 + 老节点无 `summary` 的兜底（回退到 ① 窗口）。
  - 摘要有损、会累积漂移：摘要里**强制保留「关键实体 / 未回收伏笔」清单**而非纯散文。
  - 一次调用既写剧情又更新摘要可能互相拖累质量；若明显下降，改为摘要单独低温调用（退化为"每步+1次"成本）。

### ③ RAG 语义检索（长线、支线复杂时叠加）

- 把历史节点正文向量化（embedding + 向量库）；续写时按与"当前选择/局势"的相关性**召回 top-k 段**补进上下文。
- 定位：**不替代 ④，而是与 ④ 叠加**——④ 管"大局连贯"（摘要），③ 管"精确回忆"（按需召回被折叠的具体细节）。
- 成本：需引入 embedding 模型 + 向量存储（pgvector 或独立向量库），工程量最大，demo 阶段偏重。

## 演进路线建议

**① 窗口（现在）→ ④ 树上增量摘要（作品变长后）→ ③ 检索补细节（支线/伏笔复杂后）。**
终态是 **④ 打底 + ③ 按需补**，① 作为老数据/摘要缺失时的兜底始终保留。
